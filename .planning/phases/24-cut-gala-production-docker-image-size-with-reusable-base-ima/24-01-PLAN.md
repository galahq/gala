# Plan 24-01: Production Dockerfile Split and Runtime Image Pruning

<objective>
Create the production-only Docker build path for Gala without disturbing the existing development/local Docker behavior. Add `Dockerfile.production-base` for stable runtime/system dependencies and `Dockerfile.production` for the app image, then prune build-only weight from the final production image while preserving current Rails runtime behavior.
</objective>

<threat_model>
- Build context and image layers must not include secret-bearing files such as `.env`, `.env.dev`, `.envrc`, `config/master.key`, Rails credentials plaintext, local AWS files, or Heroku config values.
- Production image changes must not mutate Heroku production at `https://www.learngala.com`, the Heroku database/cache, SES, or the retained `msc-gala` ActiveStorage media bucket.
- Runtime package pruning can break PDF generation, image processing, static asset serving, ActiveStorage variants, database restore tooling, or Rails boot if done aggressively. Keep proven runtime dependencies until route evidence proves they are removable.
- Final runtime must not depend on Node.js or pnpm after assets are precompiled; if runtime execution unexpectedly invokes JS tooling, treat that as a blocker to resolve deliberately rather than silently keeping Node.
</threat_model>

- **D-06:** Add `Dockerfile.production` and `Dockerfile.production-base`.
- **D-08:** Preserve current runtime behavior exactly, including entrypoint behavior, Puma/Sidekiq commands, Rails environment contract, and asset compile expectations.
- **D-09:** Keep production Dockerfiles production-only.
- **D-10:** Version the reusable base image with explicit tags tied to Ruby, Node, Debian, and system dependency versions.
- **D-11:** Rebuild the base image manually and infrequently when runtime dependencies change.
- **D-14:** Remove Node.js and pnpm from the final production runtime image.
- **D-15:** Keep proven runtime packages first, including PDF/image/font dependencies such as `wkhtmltopdf`, fonts, and `libvips`, unless route evidence proves unused.
- **D-16:** Conservatively remove build-only packages, package caches, `.git`, `node_modules`, temporary build dirs, test dirs, and development-only caches while preserving Rails runtime source.
- **D-17:** Evaluate Thruster only as a bounded optional check; do not add it unless it improves runtime/deploy shape without size or behavior risk.
</must_haves>

<tasks>

## Task 1: Add production base Dockerfile

<action>
Create `Dockerfile.production-base` from the runtime/system-package portion of the current `Dockerfile`, but keep it scoped to stable production base dependencies. Include Ruby 4.0.3, Debian Bookworm slim, Bundler baseline, jemalloc, PostgreSQL client support, certificate/curl support, and proven runtime packages such as `libvips`, `wkhtmltopdf`, and fonts.
</action>

<details>
- Do not copy app source into the base image.
- Do not install app gems or Node packages into the base image.
- Do not include Node.js or pnpm in the final runtime base unless the production app build stage needs a separate build-only source.
- Add comments documenting when the base image tag should change: Ruby version, Debian base, PostgreSQL client major, or runtime system package set changes.
</details>

<acceptance_criteria>
- `Dockerfile.production-base` builds independently for `linux/amd64`.
- The base image contains runtime system libraries but not app source, `node_modules`, pnpm store, or development/build toolchains.
- The file documents the explicit base-image tagging convention for downstream deploy work.
</acceptance_criteria>

## Task 2: Add production app Dockerfile

<action>
Create `Dockerfile.production` as a production-only multi-stage Rails build. Use a build stage for Node.js, pnpm, Bundler, native build packages, Bootsnap precompile, and Rails asset precompile. Use `ARG GALA_PRODUCTION_BASE_IMAGE` for the final runtime stage and fail clearly if it is not provided.
</action>

<details>
- Use the existing Ruby, Node, pnpm, Bundler, Rails, Shakapacker, and asset-precompile behavior as the compatibility baseline.
- Use `SECRET_KEY_BASE_DUMMY` or an equivalent dummy secret approach for asset precompile only; do not require real production secrets at build time.
- Copy compiled assets, packs, application source, and installed production gems into the final runtime image.
- Do not copy build-only Node/pnpm binaries, `node_modules`, pnpm store, compiler packages, apt caches, Bundler caches, test artifacts, or `.git` into final runtime.
- Preserve `ENTRYPOINT ["./entrypoint.sh"]` and `CMD ["bundle", "exec", "puma", "-C", "config/puma.rb"]` unless code evidence shows the current production path uses a different command.
</details>

<acceptance_criteria>
- Production app image builds locally when `GALA_PRODUCTION_BASE_IMAGE` points to the locally built base image.
- Final runtime image does not include `node`, `pnpm`, `node_modules`, or compiler toolchains.
- Rails assets are precompiled in the build stage and available in the final image under existing paths.
- `entrypoint.sh` behavior remains compatible for production runtime; no Heroku production behavior is changed.
</acceptance_criteria>

## Task 3: Tighten Docker build context safely

<action>
Update `.dockerignore` to remove known bulky or secret-bearing paths from the build context while preserving files required by production asset compilation and Rails boot.
</action>

<details>
- Ensure `.git`, `.planning/logs`, local env files, editor state, coverage, temporary dirs, test outputs, local package caches, and generated artifacts are excluded.
- Preserve files needed for production build: Rails app source, config, public static assets needed at runtime, `Gemfile.lock`, `package.json`, `pnpm-lock.yaml`, Shakapacker/Webpack config, and `db/sqldump/seed.dump` if the deploy path still needs it inside the image.
- Do not remove `db/sqldump/seed.dump` unless deploy code proves the seed path now comes only from S3.
</details>

<acceptance_criteria>
- Production builds still have every file required for bundle install, pnpm install, asset precompile, Rails boot, and current seed/restore behavior.
- Secret-bearing local files remain excluded from the build context.
- The phase summary can report the before/after build context size if collected during execution.
</acceptance_criteria>

## Task 4: Evaluate optional Thruster without expanding scope

<action>
Perform a bounded check of whether adding 37signals Thruster helps Gala's production runtime shape without adding meaningful image size or behavior risk. Do not add it unless the evidence is favorable and the deploy/runtime contract remains unchanged.
</action>

<acceptance_criteria>
- The executor records either "Thruster not added" with reason, or a minimal implementation with explicit before/after image-size and runtime-risk notes.
- No new runtime component is added without clear benefit and validation path.
</acceptance_criteria>
