# Plan 24-02: Deploy Integration, Shared SST Image, and Dev ECR Size Proof

<objective>
Wire the production Docker build path into the AWS/SST deployment flow, make dev-stage deploy validation use `Dockerfile.production`, and prove the compressed dev ECR production image is `<= 1.5GB`. Ensure SST services and tasks reuse a single release app image where possible instead of creating duplicate large Docker assets.
</objective>

<threat_model>
- Deployment changes must remain isolated to AWS/SST dev validation unless production is explicitly approved. Do not mutate Heroku production, the Heroku database/cache, SES, or the retained `msc-gala` media bucket.
- Cloudflare credentials, AWS secrets, Rails secrets, and `USER_DATA` values must not be printed in logs or embedded in image layers.
- A missing or stale base image can create non-reproducible builds. Production builds must require `GALA_PRODUCTION_BASE_IMAGE` and fail clearly when absent.
- SST image refactoring can accidentally build one Docker image per service/task. The plan must preserve one shared release image URI for compatible web, worker, migration, seed, refresh, and maintenance uses.
</threat_model>

<must_haves>
- **D-01:** The hard success metric is compressed AWS ECR image size `<= 1.5GB`.
- **D-02:** Proof must come from a dev ECR image using AWS image-size evidence.
- **D-03:** Keep trimming until compressed dev ECR image size is `<= 1.5GB`; do not accept near misses.
- **D-04:** Record before/after ECR sizes and exact measurement commands in the phase summary.
- **D-07:** Wire dev deploy validation to use `Dockerfile.production` during this phase.
- **D-10:** Use explicit base image tags tied to runtime/system dependency versions.
- **D-12:** Store the reusable base image in the same AWS ECR account/repository family as Gala deploy images under `AWS_PROFILE=gala`.
- **D-13:** Require `GALA_PRODUCTION_BASE_IMAGE`; fail clearly if missing.
- **D-14:** Final production runtime must not include Node.js or pnpm.
- **D-16:** Keep cleanup conservative and preserve Rails runtime source.
</must_haves>

<tasks>

## Task 1: Teach deploy script about production Dockerfiles and base image

<action>
Update `scripts/deploy-sst.sh` so app image builds use `Dockerfile.production` for AWS deploys and require `GALA_PRODUCTION_BASE_IMAGE` for non-dry-run production-image builds. Add a deliberate base-image build/push path only if needed for dev validation, with explicit tags and no `latest` dependency.
</action>

<details>
- Keep default `STAGE` choices restricted to `dev` and `production`.
- Keep read-only/local AWS command prefix behavior: `AWS_PROFILE=gala AWS_REGION=us-west-2 SST_STAGE=dev` for operator dev checks.
- Add variables such as `GALA_PRODUCTION_DOCKERFILE`, `GALA_PRODUCTION_BASE_DOCKERFILE`, and `GALA_PRODUCTION_BASE_IMAGE` only if they reduce ambiguity; do not add secret-like variables.
- Ensure `docker buildx build` or `docker build` command passes `--file Dockerfile.production` and the required base-image build arg.
- Mask or avoid printing secret-bearing environment values.
</details>

<acceptance_criteria>
- Dev deploy path builds and pushes the app image from `Dockerfile.production`.
- Missing `GALA_PRODUCTION_BASE_IMAGE` fails before a long build starts.
- The script records or prints the ECR image URI/tag needed by SST without exposing secrets.
- Existing deploy safety checks against Heroku database/cache env vars remain intact.
</acceptance_criteria>

## Task 2: Make SST consume one shared release image

<action>
Update `infra/sst.config.ts` so compatible ECS services and one-off tasks consume the same release image URI produced by the deploy script rather than causing SST to synthesize separate large Docker image assets per task.
</action>

<details>
- Preserve current web, worker, migration, seed, index refresh, weekly report, and maintenance command behavior.
- Prefer one image URI input such as `GALA_WEB_IMAGE_URI` or a more general `GALA_APP_IMAGE_URI`; if renaming, keep backward-compatible aliases where needed for existing deploy scripts.
- Do not introduce new SST stages for branch previews; previews remain `SST_STAGE=dev` with branch-derived hosts.
- Keep AWS-generated database/cache values as the source for AWS runtime; do not copy Heroku `DATABASE_URL`, `REDIS_URL`, `REDIS_HOST`, or cache values.
</details>

<acceptance_criteria>
- SST no longer creates duplicate Docker asset builds for web/worker/migration/maintenance when a shared image URI is provided.
- Web and worker services still use their existing commands and environment contracts.
- Migration/seed/maintenance tasks still run their intended commands from the same app image.
- Production remains gated; dev is the validation target for this phase.
</acceptance_criteria>

## Task 3: Wire GitHub deploy and preview workflows

<action>
Update `.github/workflows/deploy.yml` and `.github/workflows/preview.yml` so they pass the production Docker/base-image configuration into `scripts/deploy-sst.sh` for `dev` validation and production-capable deploys, while preserving the existing minimal workflow inputs and contributor authorization gates.
</action>

<details>
- Do not add manual workflow inputs beyond the Phase 23 allowed set unless strictly necessary; prefer environment variables or deterministic computed values.
- Keep Cloudflare variable requirements explicit and non-ambiguous, but do not print secret values.
- Preserve existing `branch`, `stage`, `dry_run`, `invalidate_cache`, and `user_data` input surface for deploy workflow.
- Preserve preview workflow behavior for PRs and `workflow_dispatch`.
</details>

<acceptance_criteria>
- Preview workflow uses `SST_STAGE=dev` and production Dockerfile image build path.
- Deploy workflow can use the same build path for both `dev` and `production`, with production still requiring explicit operator selection.
- Cloudflare account/token variable usage remains documented by name only and does not expand into ambiguous duplicate requirements.
</acceptance_criteria>

## Task 4: Capture dev ECR compressed size proof

<action>
After the production Dockerfile path is wired, push a dev-stage image to ECR and record compressed ECR size evidence in the Phase 24 summary. If compressed size is above `1.5GB`, return to Plan 24-01 pruning targets and keep trimming safely.
</action>

<details>
- Use `AWS_PROFILE=gala AWS_REGION=us-west-2 SST_STAGE=dev` for operator AWS CLI checks.
- Record before/after size evidence if the previous image tag/repository is available.
- Use AWS ECR `imageSizeInBytes` as the hard proof source.
- Local Docker size and history may be included as diagnostics, but they are not the gate.
</details>

<acceptance_criteria>
- Phase summary includes exact AWS CLI command(s), repository/tag checked, image size in bytes, and human-readable GB/MB conversion.
- Compressed ECR image size is `<= 1.5GB`.
- If size remains above target, execution does not mark the phase complete.
</acceptance_criteria>
