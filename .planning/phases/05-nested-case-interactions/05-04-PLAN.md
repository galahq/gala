# Phase 05 Plan 04: Wikidata, SPARQL, Locks, Tags, and Final QA Gate

<objective>
Stabilize and document the remaining Phase 5 metadata and risk-heavy route groups: Wikidata links, SPARQL, locks, taggings, and final route evidence, while keeping known security/performance concerns separate unless they directly block upgrade stabilization.
</objective>

<must_haves>
## Truths

- D-03: Browser writes are limited to lower-risk reversible interactions: comments, tags, locks, and possibly Wikidata links.
- D-06: Wikidata/SPARQL is inspected after visible content, stats/map, and quiz flows.
- D-07: Protected lock/tag/Wikidata browser checks require `/readers/sign_in` and `a.oauth-icon-google`.
- D-09: SPARQL malformed input, lock class resolution, link expansion fetch safety, stats HTML replacement, Mapbox local style noise, and legacy React warnings are documented unless blocking.
- D-11: Non-blocking known concerns are recorded in Phase 5 QA evidence with route, symptom, and suggested future hardening scope.
- D-12: Planning watches all current concern-map risks.
- D-14: Existing React 16 warnings, accepted local Mapbox production-style 404s, and third-party/browser noise are recorded but do not fail unless visible behavior breaks.
- D-15: Deeper interaction checks are required for Wikidata search/add and lock/tag controls.
- D-17: Screenshots are captured only for ambiguous visual regressions, failures, or before/after fixes.

## UI Contract

- Wikidata search/add/remove/sort UI renders without blank widgets when SPARQL returns empty/error.
- Tag and lock controls remain compact, reversible where tested, and aligned with current case editor behavior.
- Final QA evidence covers every Phase 5 route group and classifies console/network findings.
</must_haves>

<threat_model>
## Threat Model

| ID | Severity | Threat | Mitigation in Plan |
|----|----------|--------|--------------------|
| T-05-13 | high | `LocksController#set_lockable` dynamic constantization could expose unintended model lookup or action surfaces. | Document as known risk unless active protected action exposure is found; add request coverage for invalid lockable type returning `422` if missing. |
| T-05-14 | medium | SPARQL/Wikidata remote or malformed input failures could blank the UI or produce 500s. | Add request coverage or QA notes for empty/error behavior; fix only route 500/blank/blocking failures. |
| T-05-15 | medium | Wikidata/tag browser writes could leave persistent local data changes. | Only perform reversible writes and record cleanup result; prefer specs/API checks for create/destroy behavior. |
| T-05-16 | low | Final QA could pass despite unclassified console/network errors. | Final gate requires route coverage table with blocking/accepted/follow-up classification for every Phase 5 route group. |
</threat_model>
