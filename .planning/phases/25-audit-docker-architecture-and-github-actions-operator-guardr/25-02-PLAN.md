# Plan 25-02: Manual Operator Workflows and Guarded Maintenance Actions

<objective>
Implement the manual GitHub Actions operator workflow surface and supporting shell helpers. Split high-risk operator intents into distinct manual workflows, keep maintenance operations explicit, and ensure production Rails work runs inside ECS tasks rather than directly from GitHub runners.
</objective>

<threat_model>
- A broad workflow with an `operation` input can obscure side effects and let operators accidentally run production mutations.
- A workflow triggered by `pull_request` or `push` can mutate AWS without a deliberate manual dispatch.
- Production mutations can be started by a contributor who has write access but is not a CODEOWNER or environment approver.
- Freeform one-off scripts can become arbitrary shell execution against production secrets.
- Running `bundle exec rails`, `rails runner`, or `rake` directly on a GitHub runner against production DB/Redis bypasses the ECS task image, IAM, network, and secrets boundary.
- Rollback can leave assets, caches, DB migrations, or environment state inconsistent if the workflow does not state its rollback lane and verification outputs.
</threat_model>

- **D-05:** Every operator workflow exposes dry-run behavior and side-effect summaries.
- **D-06:** Production mutations require CODEOWNER-only gate plus exact typed confirmation.
- **D-08:** Rollback supports ECS task-definition rollback for immediate recovery.

- **D-11:** Migrations and one-off scripts use ECS one-off tasks.

- **D-13:** One-off script support is hard-coded and allowlisted.
- **D-15:** Maintenance exposes `rails_cache_clear`, `cloudfront_invalidate`, and `both`.

## Task 3: Add rollback workflow

<read_first>
- `infra/sst.config.ts`
- `scripts/deploy-sst.sh`
- `.github/workflows/deploy.yml`
- `docs/ops/workflows/operator-guardrails.md`
</read_first>

<action>
Create `.github/workflows/rollback.yml` for manual rollback. It must support an immediate ECS task-definition rollback lane for web and worker services and a release/image/artifact redeploy lane for reproducible recovery or drift repair. Both lanes must support `dry_run` and production typed confirmation.
</action>

<acceptance_criteria>
- `.github/workflows/rollback.yml` exists with `workflow_dispatch`.
- Inputs distinguish rollback lane: ECS task definition revision vs release/image/artifact redeploy.
- Dry run prints target cluster, service names, current task definitions, requested task definition revisions or release IDs, and commands that would run.
- Mutating ECS rollback uses `aws ecs update-service --task-definition` or a helper that resolves to that operation.
- The workflow states that task-definition rollback does not roll back database migrations, Rails cache, CloudFront cache, or static asset prefixes unless separate actions are run.
- Production mutation requires typed confirmation and appropriate environment/CODEOWNER gate.
</acceptance_criteria>

</action>

<acceptance_criteria>
- `.github/workflows/maintenance.yml` exists with `workflow_dispatch`.
- Maintenance inputs include `stage`, `dry_run`, operation/mode, and exact typed confirmation for production mutation.
- Modes include `rails_cache_clear`, `cloudfront_invalidate`, and `both`.
- Migration and one-off operations call ECS task execution using task definitions/outputs from `infra/sst.config.ts` or `scripts/deploy-sst.sh`.
- No workflow step runs production `bundle exec rails`, `rails runner`, or `rake` directly from the GitHub runner against production DB/Redis.
- One-off operations are hard-coded and allowlisted; no arbitrary shell string is executed.
- CloudFront invalidation prints distribution IDs and path scope before mutation.
- Rails cache clear prints target stage and execution boundary before mutation.
</acceptance_criteria>
