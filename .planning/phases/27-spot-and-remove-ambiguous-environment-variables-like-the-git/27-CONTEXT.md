# Phase 27: Spot And Remove Ambiguous Environment Variables Like The Git - Context

**Gathered:** 
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 27 delivers task-definition environment hygiene for the AWS/SST Rails runtime. The phase is scoped to spotting and removing ambiguous blank-like environment entries, especially `GIT_*` style metadata entries, from ECS task definitions generated by `infra/sst.config.ts`.

The phase must preserve the existing AWS deployment safety boundary: no Heroku production mutation, no `.com` DNS cutover, no deploy execution, no secret values in docs/logs, and no reuse of Heroku database/cache configuration. The source of truth remains SST IaC; verification uses static source assertions and read-only `sst diff --stage dev` evidence.

</domain>

<decisions>
## Implementation Decisions

### Blank Environment Value Semantics
- **D-01:** Treat blank-like task-definition environment values as invalid noise: `""`, whitespace-only strings, `null`, and `undefined` should not be emitted into ECS container environment arrays.
- **D-02:** Apply the cleanup rule broadly to task-definition environment entries, not only to `GIT_*` variables. `GIT_*` entries are the motivating example because blank Git metadata is ambiguous in deployed task definitions.

### Source-of-Truth Boundary
- **D-03:** Use `infra/sst.config.ts` as the implementation source of truth for task-definition environment generation.
- **D-04:** Do not mutate live AWS services, Heroku production, production DNS, or deploy workflows during this phase.
- **D-05:** Use read-only `sst diff --stage dev` evidence after source cleanup to prove the rendered infrastructure path is sane.
- **D-06:** Do not require read-only AWS ECS task-definition inspection for this phase unless execution discovers that `sst diff` cannot provide enough evidence.

### Exception Policy
- **D-07:** Do not create a blank-env allowlist. Blank-like env values should be removed categorically from generated task-definition environment data.
- **D-08:** If a future feature needs an intentionally blank value, it should introduce an explicit non-blank sentinel or a separately documented phase. This phase should not preserve blank values by comment or exception.

### Verification Gate
- **D-09:** Phase completion requires static source assertions that blank-like environment entries are filtered before ECS task definitions are produced.
- **D-10:** Phase completion also requires a read-only `sst diff --stage dev` run with the established AWS context (`AWS_PROFILE=gala`, `AWS_REGION=us-west-2`, `SST_STAGE=dev`) and no deploy.
- **D-11:** Verification should inspect the diff/report output for absence of deploy/mutation commands and for no obvious destructive changes introduced by the cleanup.

### the agent's Discretion
- The planner may choose whether the blank filtering is implemented as a small helper, normalization function, or object construction pattern, provided task-specific commands and runtime behavior stay explicit.
- The planner may choose exact static assertion commands, but they must be deterministic and should avoid printing secret values.
- The planner may add narrowly scoped tests or script checks if they are cheaper and clearer than relying on TypeScript alone.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `infra/sst.config.ts`: contains the shared Rails runtime environment, runtime secrets, service defaults, task defaults, and ECS service/task definitions that can filter blank-like env values before emission.
- Phase 26 shared task-default structure: provides the right central place to remove blank env noise once rather than patching each web/worker/task definition separately.
- `scripts/deploy-sst.sh`: provides established safe AWS/SST environment conventions and guards, but deploy execution remains out of scope.

### Established Patterns
- AWS/SST execution uses explicit `AWS_PROFILE=gala`, `AWS_REGION=us-west-2`, and stage-specific `SST_STAGE` context.
- Heroku production and `.com` DNS are not mutation targets for AWS platform phases.
- Sensitive values should be referenced by name only; do not print or persist secret values in planning docs, logs, or report artifacts.
- Task-specific commands should remain explicit and auditable even when shared environment/default helpers are used.

### Integration Points
- `sst diff --stage dev` is the read-only rendered IaC evidence for this phase.
- ECS task-definition environment output is affected by the SST service/task definitions in `infra/sst.config.ts`.
- CI/reporting integration is not required for this phase, but static checks should be easy to fold into Phase 26's advisory CI workflow later.

</code_context>

<specifics>
## Specific Ideas

- Prefer a central helper that filters object entries or environment maps before they are handed to SST's ECS/service/task configuration.
- Treat blank Git metadata as worse than absent metadata because an empty `GIT_*` value looks intentional in ECS but carries no useful information.
- Keep verification terse: source assertion plus `sst diff --stage dev`; do not expand into live AWS task-definition auditing unless the diff path is insufficient.

</specifics>

<deferred>
## Deferred Ideas

- Live AWS ECS task-definition inspection is deferred unless `sst diff` cannot provide adequate evidence.
- Adding CI enforcement for blank env values is deferred unless Phase 27 execution finds a small, stable check worth adding immediately.

</deferred>
