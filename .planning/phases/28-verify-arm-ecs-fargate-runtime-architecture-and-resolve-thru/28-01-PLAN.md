# Plan 28-01: Add explicit container architecture controls

<objective>
Make Gala's CPU architecture selection explicit across SST and deploy tooling,
then prove the production ECS-only image rollout path cannot silently perform a
first architecture transition.
</objective>

In `infra/sst.config.ts`, compute one `containerArchitecture` value from that env var and feed it into shared `railsTaskDefaults` so web, worker, migration, seed, refresh, and scheduled tasks share one source. In `scripts/deploy-sst.sh`, map `x86_64 -> DOCKER_PLATFORM=linux/amd64 -> ECS runtime X86_64` and `arm64 -> DOCKER_PLATFORM=linux/arm64 -> ECS runtime ARM64`; reject any other value before Docker build, ECR push, SST deploy, or ECS-only rollout. Propagate `GALA_CONTAINER_ARCHITECTURE` through `run_sst_cmd`. Add workflow inputs/env only where needed for operator selection without weakening current confirmations or secret handling.
  </action>
  <verify>
  `cd infra && npm exec tsc -- --noEmit`
  `bash -n scripts/deploy-sst.sh`
  `ruby -e 'require "yaml"; %w[.github/workflows/deploy.yml .github/workflows/preview.yml .github/workflows/promote-production.yml].each { |f| YAML.load_file(f); puts f }'`
  `rg -n "GALA_CONTAINER_ARCHITECTURE|DOCKER_PLATFORM|linux/arm64|linux/amd64|containerArchitecture|architecture" infra/sst.config.ts scripts/deploy-sst.sh .github/workflows`
  </verify>
  <acceptance_criteria>
  - `railsTaskDefaults` uses the computed architecture instead of hard-coded `"x86_64"`.
  - `scripts/deploy-sst.sh` validates `GALA_CONTAINER_ARCHITECTURE` and uses `--platform "$DOCKER_PLATFORM"`.
  - `run_sst_cmd` passes `GALA_CONTAINER_ARCHITECTURE` to SST.
  - Workflow changes preserve existing manual confirmation and secret boundaries.
  </acceptance_criteria>
  <done>Architecture selection is one validated path from workflow/script input to Docker platform and SST task architecture.</done>

<task id="28-01-03" type="auto">
  <name>Block ECS-only architecture transitions</name>
  <files>scripts/deploy-sst.sh, docs/ops/workflows/operator-guardrails.md</files>
  <read_first>
  - `scripts/deploy-sst.sh`
  - `.github/workflows/deploy.yml`
  - `.github/workflows/promote-production.yml`
  - `docs/ops/workflows/operator-guardrails.md`
  </read_first>
  <action>
  Treat `GALA_ECS_ONLY_DEPLOY=true` as an image-only rollout path. Before ECS-only dry run or live rollout proceeds, inspect the current web and worker service task definitions with `aws ecs describe-task-definition` and compare `taskDefinition.runtimePlatform.cpuArchitecture` to the expected runtime architecture from `GALA_CONTAINER_ARCHITECTURE`. Refuse if either current task definition differs, with a message naming `GALA_CONTAINER_ARCHITECTURE`, `GALA_ECS_ONLY_DEPLOY`, and the full SST task-definition transition path. Keep existing ECS-only rollout behavior unchanged when current task definitions already match.
  </action>
  <verify>
  `bash -n scripts/deploy-sst.sh`
  `rg -n "runtimePlatform|cpuArchitecture|GALA_ECS_ONLY_DEPLOY|GALA_CONTAINER_ARCHITECTURE|describe-task-definition|full SST" scripts/deploy-sst.sh docs/ops/workflows/operator-guardrails.md`
  </verify>
  <acceptance_criteria>
  - ECS-only dry run and live rollout both check web and worker task-definition architecture.
  - Mismatched current architecture refuses before registering or updating services.
  - Matching current architecture preserves existing image-only rollout behavior.
  - Operator docs state first architecture transition must use full SST task-definition deployment.
  </acceptance_criteria>
  <done>ECS-only rollout cannot be used for the first ARM64 transition.</done>
</task>
