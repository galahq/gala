# Plan 31-01 - Fix SST sign-in origin handling

## Goal

Close F-01 by ensuring SST dev and production runtime configuration preserves HTTPS request semantics for Devise CSRF origin checks.

## Steps

1. Compare previous branch commits and `.planning` state to preserve Phase 30 deployment guardrails.
2. Use AWS CLI/CloudWatch to identify the failing request and inspect dev/production ECS task runtime environment.
3. Update `infra/sst.config.ts` so `FORCE_SSL` is true when the effective `BASE_URL` starts with `https://`, not only when `SST_STAGE=production`.
4. Add a Devise sign-in request regression with CSRF origin checking enabled for the dev preview host.
5. Extend deploy guard coverage for dev HTTPS and dev HTTP ECS-only payload behavior.
6. Run targeted Ruby, deploy guard, infra TypeScript, and planning validation gates. Supply the dev HTTPS URL through `GALA_TEST_DEV_HTTPS_BASE_URL` for deploy guard payload checks.
7. Commit the fix with finding ID `F-01`, then validate the GitHub preview deployment and AWS runtime state.

## Acceptance Criteria

- `infra/sst.config.ts` remains the SST infrastructure authority for dev and production candidates.
- Dev preview deploys with `GALA_BASE_URL=https://...` produce `FORCE_SSL=true`, and tests receive the preview URL through an environment variable instead of a branch-specific literal.
- HTTP dev base URLs can still keep `FORCE_SSL=false`.
- Production keeps `FORCE_SSL=true`.
- `/readers/sign_in` no longer fails CSRF origin validation when the request origin and public HTTPS base URL match.
- No Heroku commands or mutations are used.
