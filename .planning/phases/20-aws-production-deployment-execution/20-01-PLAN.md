# Plan 20-01: Execute AWS Production Deployment Through SST

## Objective

Execute a non-disruptive AWS deployment path that:

- runs through SST IaC from `.github/workflows/deploy.yml`,
- keeps `https://www.learngala.com` served by the current Heroku app until a separate DNS cutover is approved,
- uses the generated AWS ALB URL as the test entrypoint for the new environment,
- uses `SST_STAGE=production` for the isolated AWS stage,
- uses SST-provisioned database and cache connection strings instead of Heroku production `DATABASE_URL` or Redis values,
- initializes the AWS database from `db/sqldump/seed.dump`,
- reuses/imports existing AWS resources where required without destructive mutations,
- keeps existing ActiveStorage S3 objects intact,
- and keeps deployment rollbacks fast through SST/ECS deployment state and immutable image tags.

## Audit Findings

| Finding | Severity | Required Correction |
| --- | --- | --- |
| Phase 20 still described a local script-first deployment path. | High | Treat `.github/workflows/deploy.yml` and `scripts/deploy-sst.sh` as the deploy entrypoint; local scripts are support tooling only. |
| Production `BASE_URL` fallback in `infra/sst.config.ts` is not the generated ALB URL. | High | Require ALB URL output capture and runtime `BASE_URL`/`ALB_BASE_URL` handling before test acceptance. |
| Heroku secret copy scope was too broad. | High | Copy retained secrets from `heroku --app msc-gala` except `DATABASE_URL`, `REDIS_HOST`, `REDIS_URL`, or equivalent cache/database connection strings. |
| Database seed restore was not tied to the SST-provisioned database output. | High | Initialize from `db/sqldump/seed.dump` only into the fresh AWS database connection generated by SST. |
| Existing AWS resource handling needs explicit import/reference rules. | Medium | SST must import or reference existing AWS resources such as `msc-gala`, SES/Gmail-related credentials, and retained S3 resources without delete/recreate operations. |
| ActiveStorage safety must be proven before route validation. | Medium | Keep existing objects intact and validate additive-only S3 operations before accepting the deployment. |

## Execution tasks

1. **Harden the GitHub Actions SST deploy gate**
   - Verify `.github/workflows/deploy.yml` is the only approved production deploy entrypoint for this phase.
   - Keep current `production` stage references aligned with `SST_STAGE=production`.
   - Keep the refusal for destructive removal of the isolated AWS stage.
   - Confirm the workflow deploys from the requested branch and calls `scripts/deploy-sst.sh`.
   - Ensure all AWS/SST commands are invoked with `AWS_PROFILE=gala AWS_REGION=us-west-2 SST_STAGE=production`.
   - Add or verify a preflight step that blocks production deploy if the secret-sync plan includes Heroku `DATABASE_URL`, `REDIS_HOST`, `REDIS_URL`, or other Heroku database/cache values.
   - Require AWS OIDC identity validation before deploy.

2. **Correct SST runtime ownership**
   - In `infra/sst.config.ts`, keep `DATABASE_URL` sourced from the SST `Postgres` resource.
   - Keep `REDIS_URL` sourced from the SST `Redis`/Valkey resource.
   - Do not read Heroku database/cache strings into ECS web, worker, migration, or scheduled-task environments.
   - Make the production `BASE_URL` test value use the generated ALB URL or a workflow-supplied `ALB_BASE_URL` after deployment output capture.

3. **Import or reference existing AWS resources safely**
   - Treat `msc-gala` as the retained ActiveStorage media bucket unless a separate migration plan changes it.
   - Import/reference existing S3, SES, Gmail-related, and other retained AWS resources instead of recreating or deleting them.
   - Ensure SST removal policy for production remains `retain`.
   - Confirm S3 policies grant only the required application access and do not delete, empty, lifecycle-expire, or publicly expose existing ActiveStorage objects.

4. **Hydrate non-database secrets from Heroku read-only config**
   - Use `heroku --app msc-gala config:get <KEY>` for every read-only Heroku secret lookup.
   - Retain every required production secret except Heroku `DATABASE_URL`, `REDIS_HOST`, `REDIS_URL`, and any equivalent database/cache connection string.
   - Reuse AWS SES, Gmail, S3, Mapbox, LTI, Rails, OAuth, and Sentry values only where they are still required by the AWS environment.
   - Store retained values in AWS Secrets Manager/SST secret storage without writing values to repo files or logs.

5. **Seed only the fresh AWS database**
   - Resolve database initialization input from `db/sqldump/seed.dump`.
   - Allow another dump under `db/` only when explicitly selected.
   - Restore into the SST-provisioned AWS `DATABASE_URL`.
   - Run migrations only against the AWS database after restore.
   - Record evidence that no Heroku `DATABASE_URL` was present in the restore command environment.

6. **Deploy and validate through the ALB URL**
   - Run the GitHub Actions `Deploy AWS` workflow with the intended branch, `SST_STAGE=production`, and `action=deploy`.
   - Capture SST outputs for app URL, ALB URL, migration task details, and image tag.
   - Validate `/up` and one representative app route through the generated AWS ALB URL.
   - Keep `https://www.learngala.com` unchanged and verify it still resolves to the Heroku production app during this phase.

7. **Rollback drill**
   - Record previous ECS service/task definition or SST deployment state before rollout.
   - Verify rollback to the previous image/task state.
   - Ensure rollback does not modify Heroku app config, Heroku releases, Heroku DNS, or existing S3 objects.

## Acceptance criteria

- GitHub Actions deploy path runs SST deploy for the selected branch/stage and refuses production removal.
- Every AWS CLI or SST execution command is prefixed with `AWS_PROFILE=gala AWS_REGION=us-west-2 SST_STAGE=production`.
- Every read-only Heroku CLI command uses `heroku --app msc-gala`.
- `infra/sst.config.ts` keeps database/cache URLs generated by SST and excludes Heroku database/cache strings from all AWS runtime environments.
- AWS environment is validated by generated ALB URL, not by changing `https://www.learngala.com`.
- Heroku CLI usage is read-only and scoped to `msc-gala` config reads for retained non-database secrets.
- `db/sqldump/seed.dump` initialization targets the fresh AWS database only.
- Existing ActiveStorage S3 objects remain intact; any S3 operation is additive and non-destructive.
- SST production removal policy and rollback procedure protect existing AWS resources and current Heroku production.
