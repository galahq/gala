# Phase 06 Plan 01: Auth and Profile Route Stabilization

<objective>
Stabilize representative Devise reader, profile, persona, terms-of-service, reader index/role, and magic-link routes through mock Google browser QA, targeted request coverage, and narrow Blueprint compatibility fixes for verified auth/profile visual regressions.
</objective>

<must_haves>
## Truths

- D-01: Use representative browser flows for Devise and profile/TOS routes rather than visiting every low-risk form in browser.
- D-02: Browser QA signs in through `/readers/sign_in` and clicks `a.oauth-icon-google`, using mock admin `dev@learnmsc.org`.
- D-03: Inspect representative signed-in account surfaces such as profile edit/show and terms-of-service handling, plus at least one public Devise form surface.
- D-04: Backfill route behavior, redirects, and authorization branches with targeted request/controller specs where browser coverage is repetitive or data-light.
- D-14: Auth/profile forms are second visual priority: verify form density, inputs, labels, button sizing, OAuth button presentation, flashes, and TOS flow.
- D-16: Keep visual fixes route-driven and narrow; add `.bp4-*` companions/scoped compatibility only where Phase 6 surfaces visibly need them.
- D-17: `config/routes.rb` remains the source of truth for route coverage.
- D-18: Browser QA uses `localhost:3000` for the app and `http://host.docker.internal:3000` from Playwright MCP.
- D-19: Check browser console and network errors before marking route group complete.
- D-21: Docker Compose is preferred for targeted app tests.

## UI Contract

- `/readers/sign_in` must render the compact `devise-card`, full-width email/password inputs, remember-me checkbox, primary sign-in button, Google OAuth button with 16px logo, links, flash/errors, and focus states.
- At least one public Devise form among sign-up, password reset, confirmation, or unlock must retain the same card density and Blueprint form styling.
- Profile/persona/TOS forms must retain label/input grouping, errors, primary CTA, and TOS continue button without density drift.
- Preserve localized copy and existing Blueprint/legacy `.pt-*` form semantics.
</must_haves>

<threat_model>
## Threat Model

| ID | Severity | Threat | Mitigation in Plan |
|----|----------|--------|--------------------|
| T-06-01 | medium | Browser QA could inspect protected account routes anonymously and miss signed-in visual regressions. | Start protected browser QA at `/readers/sign_in`, click `a.oauth-icon-google`, and record signed-in admin state in `06-QA.md`. |
| T-06-02 | medium | TOS/profile/persona update behavior could regress while form layout appears correct. | Run existing and added request specs for TOS/profile/persona route behavior. |
| T-06-03 | low | Broad Devise form styling fixes could alter unrelated routes. | Apply only verified scoped Blueprint compatibility changes to auth/profile views or shared styles already used by those surfaces. |
| T-06-04 | low | Public Devise route variants could be missed by a representative-only browser sample. | Add route checklist rows for all Devise reader route families and note browser sample vs spec coverage. |
</threat_model>
