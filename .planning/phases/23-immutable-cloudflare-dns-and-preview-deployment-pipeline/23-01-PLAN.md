# Plan 23-01: Cloudflare DNS, Immutable Assets, and Minimal Deploy Workflow

## Goal

Add SST-owned Cloudflare DNS and release-aware deployment mechanics without changing Heroku `.com` production.

## Tasks

1. Update `infra/sst.config.ts`.
   - Add Cloudflare provider configuration.
   - Derive release ID, preview host, base URL, and asset prefix from CI environment.
   - Switch app edge distribution to SST CDN so custom domain DNS and certificates are managed through SST.
   - Inject release metadata and release-scoped `ASSET_HOST` into Rails runtime.

2. Update `.github/workflows/deploy.yml` and `scripts/deploy-sst.sh`.
   - Reduce workflow inputs to the approved five.
   - Gate execution to write/maintain/admin contributors.
   - Generate release IDs and preview URLs in workflow.
   - Upload static assets to immutable S3 prefixes and retain 10 release namespaces per stage.
   - Use one shared SST Router CloudFront distribution for `learngala.dev`, `dev.learngala.dev`, and `*.dev.learngala.dev`; keep the validated stage app CDN unaliased for rollback/performance comparison until the Router is proven stable.
   - Support cache invalidation, preview PR comments, production releases, and hard-coded `user_data` hooks.

3. Add release and repository safety files.
   - Add CODEOWNERS for deployment-sensitive paths.
   - Add SECURITY.md and RELEASE.md.
   - Surface release URL metadata from `app/views/layouts/application.html.erb`.

4. Update GSD and codebase docs.
   - Add Phase 23 requirements and roadmap coverage.
   - Update `.planning/codebase/` and secret inventory docs for Cloudflare DNS and immutable assets.

5. Finalize role-aware cache hit strategy at both CloudFront and `Rails.cache.fetch`.
   - Extend request/response variation mapping for `/cases/:slug` and catalog JSON so cache keys and path allowlists reflect only safe combinations.
   - Document request/response variation sources for case/catalog routes from:
     - `app/models/case.rb`
     - `app/models/reader.rb`
     - `app/models/role.rb`
     - `app/models/managership.rb`
     - `app/models/editorship.rb`
     - `app/models/enrollment.rb`
     - `app/models/group_membership.rb`
     - `app/models/group.rb`
     - `app/models/deployment.rb`
     - `app/models/case_library_request.rb`
   - Map cache-safe variants for `/cases/:slug`:
      - `anonymous`: shared cache key by case content signature (`@case.id`, latest updated marker), locale, and case deployment context.
      - `reader_signed_in` with no personalized payload:
        - persona currently does not gate `/cases/:slug` payload branches by itself.
        - policy visibility and reader-level associations (`my_cases`, `enrollments`, `request_for_case`) still impact whether the request is allowed to render at all.
      - `reader_signed_in` with personalized shell payload:
        - includes `reader` + `enrollment` + `quiz` + stats branch.
        - only safe for per-reader cache keying unless we split shell and user-branch rendering.
        - `role == editor` additionally enables policy update gates and editor-only JSON keys (`statistics`).
        - `enrollment.status` (`student`/`instructor`/`treatment`) changes quiz necessity.
        - `group_membership/group.admin` + `deployment.active_group` affects case/deployment association branch.
      - `library manager`/`managership` and `case_library_request` paths:
        - response includes private visibility through policy (`CasePolicy#show?`, `CasePolicy::Scope`, request_for_case path).
        - keep these requests in signed-in, low-TTL cache buckets and avoid sharing cache artifacts across reader contexts.
      - `admin/editor` and role-`editor` from `Role`:
        - global policy override (`editor?`) means admin-scope case visibility can differ from normal readers and should remain isolated.
   - For catalog JSON endpoints (currently in `PublicCatalogCache`):
      - anonymous may stay in long-lived shared cache buckets (`30d`) where payload is global.
      - signed-in must remain in short-lived buckets due visibility branches that vary by per-reader associations unless shell/private data is separated.
   - Include roles/personas/associations that legitimately vary responses:
     - anonymous (no reader)
     - signed-in learner/teacher/writer personas (persona does not presently gate catalog or case JSON payload content)
     - rolify `editor` role (can alter response shape with privileged operations)
     - library managers (`managerships`), case editors (`editorships`), and enrolled students (`enrollments`)
     - case library request visibility (`request_for_case` path)
   - For static catalog JSON paths, keep anonymous CDN/Rails cache broad where safe.
   - For signed-in/association-dependent paths, preserve privacy by keying cache variants with explicit authorization context signatures (not raw session/cookie identity), including:
     - policy visibility buckets (`published`, `my_cases`, `enrolled_cases`, `case_library_requests`, editor gates)
     - deployment/enrollment identity and last-updated timestamps where render output includes quiz/deployment state.
   - SST StaticSite/CloudFront cache-hardening requirements for cache-safe delivery:
      - keep cacheable allowlist patterns in `orderedCacheBehaviors` unchanged (`/cases.json`, `/cases/features.json`, `/cases/*`, `/tags.json`, `/catalog/*`, `/catalog/*.json`).
      - keep explicit non-cacheable case routes excluded:
        - comments/community/deployments/quizzes/stats/edits/settings/wiki/forums/features and related sensitive mutation reads.
      - enforce static-site compression with `compress: true` and `Accept-Encoding` variation headers so browsers can negotiate Brotli (`br`) when available.
      - retain SWR behavior in `Cache-Control` for cacheable routes.
