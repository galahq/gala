# v2.0.0 WIP

This WIP release tracks the AWS/SST `.dev` migration and workflow simplification.
It is scoped to `learngala.dev`, `dev.learngala.dev`, and
`*.dev.learngala.dev` only. The existing `https://www.learngala.com` Heroku
production path is not part of this release unless a later cutover phase says so.

## Scope

- Establish explicit AWS/SST `dev` and `production` environments for the `.dev`
  domain family.
- Support ephemeral pull-request preview environments under
  `*.dev.learngala.dev`.
- Consolidate GitHub Actions to three ARM-runner workflows: `ci`, `deploy`, and
  `infra`.
- Keep `deploy` as the site-operator path with only `stage` plus optional
  `user_data`.
- Keep `infra` as a manually dispatched thin SST wrapper for `diff` and `deploy`
  with a preview checkbox.

## WIP Changes

- Rename/simplify workflow files to `.github/workflows/ci.yml`,
  `.github/workflows/deploy.yaml`, and `.github/workflows/infra.yml`.
- Standardize workflow names and job IDs to `ci`, `deploy`, and `infra`.
- Pin workflow jobs to the ARM GitHub runner `ubuntu-24.04-arm`.
- Preserve the CI validation artifact as advisory evidence while making release
  readiness explicit.
- Document the `.dev` domain, explicit environment, and PR preview boundaries.

## Release Gates

- `ci` evidence is reviewed for required-suite failures and release readiness.
- `infra` preview/diff is reviewed for infrastructure drift before mutation.
- `deploy` is exercised for `dev` before any `production` stage operation.
- Preview host behavior is verified for the relevant pull request under
  `*.dev.learngala.dev`.
- No `.com` or Heroku production mutation occurs as part of this release.

## CI validation acknowledgement checklist

Use this checklist for the final release candidate run. The GitHub check may be
green while the artifact still reports `state: failure`; the artifact is the
operator evidence source.

1. Record the exact `ci` run URL, head SHA, and artifact name.
2. Open `validation-report.txt` from the `gala-ci-<run_id>` artifact.
3. Confirm `release_readiness` is either `check` or `review_required`.
4. If `release_readiness` is `blocked`, stop and fix the non-excluded failure
   before release.
5. Review `confidence_exclusions` and acknowledge any excluded noisy dimensions.
6. Confirm excluded dimensions are limited to documented repo-wide lint/factory
   noise or optional SST evidence that is supplied separately by `infra`.
7. Attach or link the `infra` diff evidence before any mutating deploy.
8. Record the `.dev` hostnames validated for dev, production, and preview.

The confidence score is release-evidence confidence, not a release approval
score. Excluded noise remains visible in the CI matrix and still requires this
checklist acknowledgement.

## Validation confidence model

The `evidence_confidence` score is weighted toward site-outage risk, not syntax
cleanliness.

- Ruby, ESLint, stylelint, and factory lint findings remain visible in the
  artifact, but conventional style-only findings are advisory and excluded from
  confidence scoring.
- Database migrations, workflow changes, SST/infra changes, Docker/runtime
  changes, and deploy-script changes are treated as higher release risk.
- High-risk changes require stronger release evidence: successful dev-stage
  deployment, system smoke coverage, and frontend E2E coverage.
- Missing AWS/SST evidence is not style noise. If the PR touches infra or
  migrations, missing `infra`/dev-stage evidence should lower confidence.
- A production release candidate should not proceed from `review_required` or
  `blocked` until the missing risk-weighted evidence is attached.
